About the NetVote Platform

NetVote is a secure, high-concurrency, and network-aware electronic voting system. It combines atomic transaction guarantees, cryptographic ballot integrity, and real-time network telemetry into a dependable client-server architecture.

Technologies Implemented

Backend Server

Python 3 & Flask

Powers the core REST API with Werkzeug multi-threaded server architecture. Handles concurrent client connections independently with dedicated execution contexts.

Storage & ACID

SQLite in WAL Mode

Configured with Write-Ahead Logging (WAL) to enable non-blocking concurrent readers while a single writer commits. Fully enforces ACID guarantees with atomic rollback protection.

Operating Systems

Mutex & Concurrency Controls

Guards critical ballot submission paths with InstrumentedLock to completely prevent race conditions, lost updates, and duplicate votes under heavy traffic bursts.

Computer Networks

TCP Message Framing

Implements low-level socket protocol (socket(), bind(), listen(), accept(), send(), recv()) with 4-byte length prefixes to eliminate TCP byte-stream fragmentation.

Security & Cryptography

SHA-256 Hash Chaining

Ballots are linked in a cryptographic blockchain-style hash chain. Any retroactive database tampering immediately breaks the chain and flags an alert on verification.

Voter Privacy

HMAC Voter Pseudonymity

Decouples voter personal identification from candidate choices using salted HMAC keys. Preserves strict ballot secrecy while guaranteeing one voter cannot vote twice.

Network Defense

Sliding-Window Rate Limiting

Application-layer sliding window algorithm tracks request volume per IP address, stopping brute-force and credential-stuffing attacks with HTTP 429 status codes.

Distributed Reliability

Idempotency & Request Tracing

Every HTTP interaction carries a unique correlation ID (REQ-YYYY-XXXXXXXX). Replayed vote submissions return original receipts without creating duplicate ballots.

Telemetry & Frontend

Vanilla JS & Chart.js

Zero external runtime CDN dependencies. Bundles modern responsive UI with live latency percentiles (P50/P95/P99), requests-per-second, and in-flight connection tracking.

Operating Systems Engineering in Practice

Multi-Threading & Race Condition Elimination

When hundreds of voters cast ballots simultaneously, unsynchronized threads create classic check-then-act race conditions where two threads read has_voted = 0 at the same time and record duplicate votes.

NetVote enforces defense-in-depth:

  • Mutex Critical Section: An in-process lock allows only one thread inside the vote processing block at a time.
  • Immediate Transaction: SQLite BEGIN IMMEDIATE acquires the database write lock up-front.
  • Relational Constraints: A UNIQUE(voter_ref) database constraint physically rejects duplicates even if application code fails.

Deadlock, Starvation & Producer-Consumer Architecture

Robust distributed systems must prevent resource locking hazards:

  • Deadlock Prevention: Circular wait is broken using strict lock acquisition ordering and bounded timeouts.
  • Starvation Mitigation: Lock acquisition limits request waits to 10 seconds, failing gracefully with HTTP 503 instead of hanging voters.
  • Producer-Consumer Logger: Voter request threads push audit log events onto a bounded in-memory queue. A separate background worker thread batches and flushes them to disk, preventing slow disk writes from stalling voters.

Computer Networks Architecture

Client-Server Protocol & Semantic Status Codes

The system follows the REST architectural pattern over HTTP/1.1 and TCP, returning strict, standard HTTP status codes:

  • 200 OK / 201 Created — Successful data retrieval or ballot generation.
  • 400 Bad Request — Invalid parameters, malformed JSON, or missing fields.
  • 401 Unauthorized / 403 Forbidden — Unauthenticated requests or unauthorized administrative access.
  • 409 Conflict — Duplicate voting attempts or invalid candidate state transitions.
  • 429 Too Many Requests — Sliding-window rate limit exceeded.
  • 500 / 503 Unavailable — Server database locks or timeouts, with zero leaked stack traces.

TCP Message Framing & Stream Boundary Management

Because TCP is a continuous byte stream without message boundaries, two calls to send() can easily coalesce into a single recv(), or one message can arrive fragmented across packets.

NetVote implements an application-layer framing standard:

[ 4-byte big-endian length N ][ N bytes UTF-8 payload ]

The recv_exact() reader loops continuously until the exact specified frame length is assembled, guaranteeing zero data truncation or framing overlap.
